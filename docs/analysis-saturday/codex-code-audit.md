# Codex adversarial code audit

Source: Team 3 lunch review, Sat 3 Oct 2026, frozen copy of the Mini at commit fa91372, tick 630.

1. **MAJOR, agent/duel.py:1000: Acceptance can cross the utility limit despite the re-read.** Buyer limit 100, weight 3: the re-read approves `(90, 0)`, but the rival replaces it with `(99, 10)` before the POST. `duel_accept()` accepts whichever offer now stands, yielding **−29 surplus**. The late path has the same race. **CONFIDENCE: high; ran an in-memory mock reproduction.** Minimal fix: require the rival’s offer to have been posted in the current tick, consuming its message slot, and abandon acceptance if that tick can no longer be safely maintained through the POST.

2. **MAJOR, agent/duel.py:591: The allocator sacrifices the better deal when slots run out.** Two otherwise equivalent duels have one tick remaining and surpluses 50 and 5. Sorting by surplus then minimizing `left - rank` selects the **5-surplus** deal and lets the 50-surplus deal expire. **CONFIDENCE: high; ran the actual allocator with those inputs.** Minimal fix: preserve higher-surplus priority among equally urgent deadlines, particularly when remaining accepts cannot cover every duel.

3. **MAJOR, agent/duel.py:745: An improved offer can waste the final accept slot.** After allocation selects one duel, its rival improves the offer before the re-read. The changed ID causes a skip; other acceptable duels remain suppressed, and `late_pass()` reports success despite accepting nothing. At deadline−1, the available deal expires. **CONFIDENCE: high; reproduced zero accepts with two acceptable duels and improved replacement offers.** Minimal fix: re-evaluate the fresh offers and reallocate within the same tick when no acceptance was submitted.

4. **MAJOR, agent/chato.py:462 and agent/abuela.py:269: The duel lock does not stop already-running dealers.** A dealer started before a duel wave keeps accepting during it, consuming the shared slot and potentially losing a deadline-bound duel. Both clients also enable SDK `wait_on_tick` replay, so a refused accept can retry next tick without checking the newly created lock. **CONFIDENCE: high; read-only trace through both clients and SDK retry handling.** Minimal fix: check the lock before every accept, disable `wait_on_tick`, and return refused writes to the decision loop for fresh validation.

5. **MAJOR, agent/rastro_seller.py:469: A spare can become the last copy while retaining its duplicate floor.** Setup approves a duplicate worth 20 with floor 21. Another agent sells the retained copy; the remaining card is now worth 100, but `sync()` leaves its old floor and sale offers active. A 30-P sale can therefore destroy 70 P of private value. **CONFIDENCE: high; read-only verification of setup, sync, listing, and acceptance paths.** Minimal fix: recompute copy counts and values every tick, cancelling stale offers and disabling newly last copies unless explicitly allowed.

6. **MAJOR, agent/chato.py:240 and agent/abuela.py:158: Dealer limits use stale private values.** A plan values a missing card at 100. Another bot acquires it, reducing the next copy’s value to 20; these loops refresh cash but retain the original value and can accept a 90-P final offer. Cached sell values can likewise become unsafe, including with Pilar. **CONFIDENCE: high; read-only verification.** Minimal fix: refresh marginal buy values and held-asset sell values before counteroffers and accepts, preserving any stricter configured cap.

7. **MAJOR, agent/chato.py:529 and agent/abuela.py:292: Defaults block every purchase at current cash.** With 170 P and no preceding sales, reserve 280 produces −110 P spendable. Every buy target is skipped and a buy-only run completes without a deal. **CONFIDENCE: high; read-only control-flow verification and arithmetic.** Minimal fix: lower the default reserve to the actual required obligation and report an unsuccessful run when all requested purchases are blocked.

8. **MAJOR, agent/chato.py:277: The bid cap deadlocks negotiations and has already discarded an affordable deal.** Saturday thread 335 had reservation 93 and bid cap 84. Chato offered 90, nonfinal; the bot waited silently for four minutes, reached `max_rounds`, and closed. Dealers only move when the team moves. **CONFIDENCE: high; read-only verification against Saturday’s Chato log, lines 1–14.** Minimal fix: when pinned at the bid cap, accept a standing offer inside the reservation or close immediately if it is unacceptable.

9. **MINOR, agent/duel.py:406: Sunday’s 12-tick duels inherit a fictitious four-tick head start.** For a duel starting at tick 100 with deadline 112, the default duration 16 sets its start to 96. With the supplied `absent_at=0.2` parameters, it immediately posts its concession offer at tick 100 instead of listening until tick 103, allowing an opponent to take the cheaper opening. **CONFIDENCE: high; ran both configurations through the actual decision function.** Minimal fix: set the session duration to 12 for Duels III instead of retaining the 16-tick default.

NOT FOUND: Area 2, current broker `stall` matching logic. Recorded-book replay and 5,000 randomized comparisons found no current pairing, pricing, or legal-bench rejection defect; the historical `same_maker` failure is fixed.
